# M5 0.5.0 Publication Bootstrap

**State:** Accepted for the `0.5.0` release only

OxideBatch `0.5.0` is the one-time publication bootstrap for workspace crates
that do not yet exist on crates.io. crates.io Trusted Publishing can publish a
new version of an existing crate, but it cannot create a crate name. The first
release of each newly published crate therefore needs one manual bootstrap
publish from the exact reviewed release tag.

## Scope

The `0.5.0` release set is, in dependency order:

1. `oxide-batch-core`
2. `oxide-batch-repository`
3. `oxide-batch-plan`
4. `oxide-batch`
5. `oxide-batch-cli`

At the start of this bootstrap, `oxide-batch` is already owned on crates.io
from `0.1.0-alpha.1`; the other four crate names are first-publication
candidates. Treat the whole five-crate set as one release operation so that the
registry contents can be verified against the immutable `v0.5.0` tag before the
GitHub Release is published.

## Preconditions

Do not begin until all of the following are true:

- the reviewed release-preparation PR is merged;
- the merge commit is the intended `v0.5.0` release tree;
- required CI and M5 evidence are green on that tree;
- `cargo xtask package` and `cargo xtask release-crates` pass;
- the protected `v0.5.0` tag points at that reviewed commit;
- the tag-triggered draft GitHub Release was prepared successfully and its
  package, checksum, SBOM, and attestation assets were reviewed;
- a short-lived crates.io API token is available locally to the maintainer
  performing the bootstrap.

Do not store that token in the repository or as a long-lived GitHub secret.

## Bootstrap publish

Check out the immutable tag and authenticate locally:

```console
git checkout v0.5.0
cargo login
```

Publish in dependency order. Stop immediately if any command fails:

```console
cargo publish -p oxide-batch-core --locked
cargo publish -p oxide-batch-repository --locked
cargo publish -p oxide-batch-plan --locked
cargo publish -p oxide-batch --locked
cargo publish -p oxide-batch-cli --locked
```

A crate version already present on crates.io must not be blindly retried. If a
partial publication occurred, inspect the registry first and continue only with
versions that are still absent and whose dependencies are already available.
Published crates.io versions are immutable.

## Configure Trusted Publishing

Immediately after each newly created crate exists on crates.io, configure its
Trusted Publisher to the same identity used by the established facade release:

- GitHub owner: `luceat-lux-vestra`
- repository: `oxide-batch`
- workflow: `release.yml`
- environment: `release`

After all five crates are present and the new crate publishers are configured,
remove the local API token with `cargo logout` and delete any temporary copy of
the token.

## Publish the GitHub Release

Only after the manual bootstrap is complete, publish the reviewed draft GitHub
Release.

For `0.5.0`, `.github/workflows/release.yml` does **not** attempt to publish the
same versions again. Instead it rebuilds all five `.crate` archives from the
immutable release tag, obtains the recorded crates.io checksum for each exact
crate/version, and fails unless every local SHA-256 matches the registry.

That makes the GitHub Release publication a fail-closed verification step for
the bootstrap rather than a second publisher.

## Later releases

`0.5.0` is the only bootstrap exception. Starting with the next release, all
five crate names already exist and the normal release workflow uses crates.io
Trusted Publishing exclusively through the OIDC `release.yml` path.

If a future milestone adds another newly published crate, that crate requires a
separately reviewed first-publication bootstrap decision; do not generalize the
`0.5.0` exception silently.

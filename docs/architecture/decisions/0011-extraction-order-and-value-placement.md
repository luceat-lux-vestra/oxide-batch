# ADR-0011: Durable Value Placement Across Extracted Boundaries

- **State:** Proposed
- **Date:** 2026-08-03
- **Owners:** architecture maintainers
- **Deciders:** project owner
- **Governing RFC:** [RFC-0003](../../rfcs/0003-target-workspace-boundaries.md)
- **Refines:** the [staged crate-extraction contract](../crate-extraction.md)

## Context

Stage 1 of the M5 extraction is complete and recorded in the
[crate-extraction evidence](../../project/m5-crate-extraction-evidence.md).
Stages 2 and 3 cannot begin, because the contract names boundary *content* in
prose and the delivered code does not divide along it.

The contract orders the stages `oxide-batch-core`, `oxide-batch-repository`,
`oxide-batch-plan`, and forbids `oxide-batch-repository` from depending on
`oxide-batch-plan`. That direction is not arbitrary: the accepted
[architecture overview](../overview.md) fixes it as the inward dependency rule,
with the compiled execution plan above the repository and transaction ports,
and `core domain, identities, and state rules` at the bottom.

Measured against the delivered code, the repository port reaches upward past
that rule:

- `RepositoryUnitOfWork` takes `NodeId` and `StartLimit` in four method
  signatures, and `RepositoryError::StartLimitExceeded` carries both. Both are
  declared in the plan module.
- The same port takes `FlowStepState`, `FlowDecision`, `FlowDecisionRequest`,
  and `FlowTransitionKind` from the flow module, and `PartitionPlanEntry`,
  `StepPartition`, `PartitionAggregate`, and `PartitionAggregationError` from
  the partition module. The partition values additionally read
  `MAX_PARTITIONS`, declared in the plan module.
- The operator, explorer, retention, and recovery descriptors the port carries
  are interleaved in `service/*.rs` with four service implementations
  — `JobExplorer`, `JobOperator`, `RecoveryProposer`, `RetentionService` —
  that depend on telemetry types whose observability boundary is deferred past
  M5.

The plan module, in turn, needs nothing from the repository module: its only
non-core dependency is `FaultPolicy`. The fault-policy values are runtime-free,
because `BoxFuture` and `StopToken` appear in the fault module only inside
`BackoffSleeper`, which no plan type embeds.

Stage 1 already resolved a small instance of this by moving `MAX_NODES` and
`MAX_TRANSITIONS` with the manifest reader that enforces them. Stages 2 and 3
are the same problem an order of magnitude larger, so they need a recorded rule
rather than a per-type judgment inside an implementation commit.

## Decision

Place every type by what it **is**, not by which module it currently sits in:

> **Durable data lives at or below the layer that persists it. Compilers,
> runtimes, and engines live above it.**

A value that is written to metadata, read back on restart, or hashed into a
definition fingerprint is domain data. It belongs in `oxide-batch-core`
regardless of which module happens to declare it today, because everything
above core — the compiler, the ports, the engines, the adapters — reads and
writes it. A value that only the plan compiler constructs and raises belongs in
`oxide-batch-plan`.

This rule reaches the same result as the accepted inward dependency rule in the
[architecture overview](../overview.md), which places `core domain, identities,
and state rules` at the bottom. That agreement is the check on the rule, not
its justification: the placement below is what the types are, and it would be
the answer even if no document had fixed a direction.

**Into `oxide-batch-core`, before stage 2.**

| Type | Why it moves | Cost |
| --- | --- | --- |
| `NodeId` | The durable logical identity of a step. Persisted on every step execution, named by four port signatures, and already generated by core's own `definition_token` macro, so its constructor already returns `DefinitionError` | None |
| `FlowTarget`, `TerminalKind` | The durable target of a recorded transition, carried inside every persisted `FlowDecision` | None |
| `StartControls`, `StartLimit` | Restart-relevant definition data enforced against persisted start counts, which `RepositoryError::StartLimitExceeded` reports. `StartControls::new` is infallible | One reviewed API change, below |
| `MAX_PARTITIONS` | A framework capability bound read by durable partition values, exactly as `MAX_NODES` was read by the manifest reader in stage 1 | None |
| The 17 fault-policy values | Restart-relevant definition data: they are fingerprint inputs under ADR-0009 and are embedded in `StepNode`. They are runtime-free — `FaultPolicy`, `FaultClassifier`, `FaultRule`, `FaultPhase`, `FaultAction`, `FaultDecision`, `FaultDescriptor`, `FaultEvidence`, `RetryLimit`, `RetryStateLimit`, `RetryOrdinal`, `SkipLimit`, `SkipCounts`, `RollbackDisposition`, `BackoffPolicy`, `BackoffKind`, `FaultPolicyError` | None |

`BackoffSleeper` and `BackoffOutcome` stay behind: they are the async waiting
contract rather than policy values.

**The one API change.** `StartLimit::new` returns `PlanError::ZeroStartLimit`,
and `PlanError` carries `NodeId` in nineteen variants and `ExitPattern` in two,
so moving the error with the type would drag the plan compiler's whole error
vocabulary into core. Instead `StartLimit::new` returns a new
`DefinitionError` variant. `DefinitionError` is `#[non_exhaustive]`, so adding
the variant is not itself a breaking change; the changed return type is, and it
is submitted as an accepted, separately reviewed API change under the
contract's own allowance. It is one constructor, pre-1.0, and no durable byte,
fingerprint, or manifest member is affected.

**Into `oxide-batch-repository`, in stage 2.** The repository, explorer,
operator, retention, recovery, and transaction ports and capability
descriptors, plus the durable record types those ports carry: the flow decision
and step-state records, the partition plan, result, and aggregate records, and
the operator, explorer, retention, and recovery descriptors with their bounds.

**Into `oxide-batch-plan`, in stage 3.** Plan compilation, graph normalization,
fingerprint projection, and the graph types that only the compiler constructs:
`PlanError`, `ExitPattern`, `PatternSpecificity`, `FlowGraph`, `FlowNode`,
`FlowTransition`, `StepNode`, `DecisionNode`, `SplitNode`, `JoinNode`,
`PartitionedStepNode`, `SplitBranch`, `SplitBudget`, `PartitionBudget`,
`PartitionCount`, `DeciderRevision`, `DecisionInputVersion`,
`LocalFailurePolicy`, `StepComponents`, `FlowSelectionError`,
`CompiledExecutionPlan`, and the remaining graph and local-scale bounds.

**The two crates become independent siblings.** After the moves above, the plan
needs nothing from the repository and the repository needs nothing from the
plan; both depend only on core. The contract's allowance for
`oxide-batch-plan` to depend on `oxide-batch-repository` is therefore tightened
to a prohibition in both directions, which is stronger, enforceable by the
dependency check, and true of the delivered code. The stage order between them
stops mattering, so it is left as the contract fixed it.

**Staying in the facade.** The four service implementations, the fault runtime
and state store, the chunk and flow engines, every adapter, telemetry, the
shutdown coordinator, and the diagnostics surface. The engine, item, adapter,
observability, test-kit, distributed-protocol, and integration boundaries
remain deferred past M5 and unauthorized.

Every stage keeps the contract's existing obligations unchanged: facade and API
equivalence, durable invariance, packaging evidence, measurements, and one
revertible commit per stage.

## Consequences

- Stages 2 and 3 become executable without overturning the accepted dependency
  rule.
- `oxide-batch-core` gains `23` items. Every one is a durable identity, a
  durable transition target, a restart-relevant definition value, or a
  framework bound — data that is persisted, replayed, or fingerprinted.
- The plan and repository crates become independent siblings over core, so the
  persistence layer never depends on the compiler and the compiler never
  depends on persistence.
- `oxide-batch-plan` keeps the compiler and the graph types only it owns, and
  loses nothing it raises errors about: `PlanError` stays with the code that
  produces it.
- One public constructor changes its error type. It needs its own review and a
  changelog entry, and it is the only public API difference the remaining
  stages introduce.
- `service/*.rs` must be split so descriptors and ports move while the four
  service implementations stay. This is the largest mechanical risk in the
  remaining work.
- The placements are expected to be final for these types. The long-term
  forecast in the
  [post-M5 strategy](../../project/post-m5-full-parity-strategy.md) predicts
  separate `oxide-batch-flow`, `oxide-batch-fault-tolerance`, and
  `oxide-batch-partition` crates, but under this rule those crates take the
  runtime machinery — `FlowLauncher`, `FaultRuntime`, `FaultStateStore`,
  `BackoffSleeper`, the partition runtime — while the durable records and
  policy values stay where this decision puts them. No type is predicted to
  move twice.
- The dependency check in `xtask/src/deps.rs` gains the rules for the two new
  crates; its existing rules are unchanged.
- Stage 1 is unaffected and is not revisited.

## Alternatives considered

- **Swap the stages so the plan is extracted second and a repository port may
  name plan types.** This moves the fewest types, keeps `NodeId`, `StartLimit`,
  `PlanError`, and `ExitPattern` together, and needs no API change. Rejected on
  the merits rather than on precedent: it makes the persistence layer depend on
  the plan compiler, so writing a step execution row would pull in graph
  normalization, exit-pattern matching, and fingerprint projection. The
  durable metadata model does not need a compiler, and a boundary that says it
  does is wrong however the stage table is written. It also leaves `NodeId` —
  the identity every persisted step execution carries — above the layer that
  persists it.
- **Move `PlanError` into core with `StartLimit`, avoiding the API change.**
  Rejected: core would declare nineteen graph-structure error variants it never
  raises, and would acquire `ExitPattern` and `PatternSpecificity` with them,
  for the sole purpose of preserving one constructor signature.
- **Change the repository port to stop naming plan types.** The port would take
  primitives instead of `NodeId` and `StartLimit`. Rejected: a much larger
  public trait change, made only to avoid moving two value types.
- **Defer stages 2 and 3 past M5.** Rejected: the milestone's exit work follows
  all implementation streams, and issue #99's exit criteria require every
  authorized stage.
- **Authorize the flow, fault-tolerance, and partition boundaries now so these
  types land in their final homes.** Rejected: those boundaries are deferred by
  the M5 design gate, and extracting them would make M5 a rewrite.

## Validation

`cargo xtask deps` enforces the boundary rules and fails on a reversed edge.
The facade public-API snapshot, golden fingerprint vectors, normalized
repository-write traces, the full suite, and `cargo xtask package` hold each
stage to the same equivalence and durable-invariance bar stage 1 met. The
`StartLimit::new` change is the one expected snapshot-adjacent difference and
carries its own review and changelog entry.

## Revisit triggers

Revisit if the flow, fault-tolerance, partition, or observability boundaries
are authorized, which changes where these types finally live and what stage 2
must leave behind; or if the repository port acquires a durable vocabulary of
its own that no longer names plan identities.
